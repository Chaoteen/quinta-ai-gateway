# Quinta AI Gateway 产品路线图

## 2026-11-09 产品决策基线（优先于下文历史路线图）

本节记录客户已确认的业务要求，不代表相关功能已经实现或验收。下文的 Alpha Ready 等历史标签不能作为上线证据。与本节冲突的旧方案需重新评估。

### 服务对象与收款

- 企业最终客户优先，其次为个人用户和智能体开发者；预计第一批约十家企业。多级转售、分销结算和租户独立收款不作为第一版主线。
- 平台公司统一采购资源、设置商品及价格，通过公司支付宝、微信及银行账户收款。企业的付款账户不是平台收款商户。
- 个人注册后可以自行充值使用；企业开通后使用企业账户，供内部各部门的 Agent 或其他应用调用。部门用量归因需要支持，复杂组织架构对接后置。
- 一个账号仅属于一家企业；个人余额、历史订单及密钥如何在企业开通时处理尚需明确，不得自动将个人资产合并进企业。
- 平台老板、财务、运营、审计通过 RBAC 分权。财务操作与跨企业支持权限须明确授权并留审计记录。
- 2026-11-09 已确认：平台有一般纳税人主体，可开普通及增值税专用发票，尚未对接开票软件。首期采用平台申请与财务真实开票登记，后续接入服务商 API；开票方案、金额口径和实现边界见 `docs/user-guide/invoice.md` 及 `docs/iteration_11_1/invoice_foundation.md` 的最新更新。

### 商品、调用与资金

- 第一版人民币，主要通过 API Key 调用；支持按量商品与月度套餐。计量单位按模型确定，不将文本 token、视频时长和生成次数混为同一单位。
- 上游可能由平台采购，也可能通过上游管理接口代建用户及 Key。客户提到 Seedance，但服务商、代建接口及 Key 交付/调用路径仍待确定；不假设该模型的任一服务商都支持代建用户。代建身份、实际请求路径、上游费用承担方、用量来源需分别建模。
- 智能体订阅包含一定调用额度（已选择方案 B），额度用尽后支持额外充值及恢复使用；订阅有效期和用量余额分别校验，充值不自动续订过期的软件授权。套餐额度的计量单位、充值后的抵扣顺序及跨周期结转规则需在商品上明确。当前要求不等于建设可视化 Agent 编排平台。
- 企业先付费，按月对账，不默认开放月结授信。余额低于约定基数的 10% 提醒；基数及通知渠道待确认。不得将人民币余额、内部 quota 与模型原始 token 数等同。
- 平台设置输入、输出、缓存、套餐及合同折扣，保存订单和消费时的规则版本，不使用退款时的最新目录价覆盖历史规则。
- 收款、额度权益、模型消费、上游成本、订阅收入和补贴应能分别追溯；已有部分加额流水不能视为完整账务实现。
- 请求失败不自动等于免费：根据可核实的上游收费结果及客户合同结算；无费用释放预留额度，未知费用进入待核实状态。请求重试与异步任务必须可追踪，防止重复扣款及重复履约。

### 补贴与退款

- 已确认补贴模式：每家企业各有月度上限，由平台减免客户支付金额，政府按月向平台报销。30%、100,000 元、半年仅是示例，不能写死；金额、币种、比例、起止日及与商业折扣的叠加方式均由政策配置。客户举例上限也可能为 1,000 美元；第一版支付仍为人民币，跨币种政策需另行明确汇率来源、锁定时点及舍入规则，禁止将美元上限当成人民币金额使用。
- 政策应区分折后金额继续补贴与商业折扣不叠加；计算顺序须展示。首个计算提案按折后合格消费计补贴、不叠加时保留商业折扣且不自动择优，金额向下取整到分，均须在正式政策中确认。合格商品、费用口径、资格审批和政策起止日由具体政策明确。
- 补贴资格、计算、预占、核销、申报、批准、到账和冲正应分别记录。申报或预计金额不能当成政府已到账资金，也不能自动转为客户可提现余额。
- 退款需客户申请。合同有时长或用量折扣承诺时，按订单约定的退订规则重算已消费费用、追回优惠，再计算可退实付资金；赠送权益与政府补贴不得直接折成客户现金。
- 待确认的默认提案：可退金额下限为零，扣除历史退款和待结算费用，原路退款；超出实付金额的差额不自动追缴，另按明确合同人工处理。智能体订阅与资源套餐分别定义退订规则。
- 参考资料只用于产品方案比较，不把云厂商的产品退订条件直接套用到本平台：阿里云 https://help.aliyun.com/zh/user-center/cancel-subscription/ ；AWS Savings Plans https://docs.aws.amazon.com/savingsplans/latest/userguide/return-sp.html 。AWS 此页只适用于符合其限制的 Savings Plans 退回，不是通用余额退款规则。

### 首页与范围

- 展示接入模型和支持的智能体；配置平台名称、Logo、联系方式、首页样式、Banner 和推广位。保留上游项目标识、许可及署名。
- 定时上下架、复杂组织架构、转售商独立收款及多级佣金后置。

### 开发与验收顺序

1. 明确个人与企业开户、成员归属、资产边界；验证注册、企业审批、越权拒绝及企业内部调用归因。
2. 重构平台统一收款边界；当前生产环境强制租户独立收款的实现与业务不符，不能直接上线，也不能简单关闭保护后启用旧支付入口。
3. 完成版本化价格、用量计量、预留与结算、订阅权益和充值恢复；验证并发、失败、断连、重试及异步任务不重复扣费。
4. 对接真实支付与银行核账；验证验签、金额与商户匹配、重复回调、到账履约、退款和账务一致性。
5. 在补贴资金流确认后实现补贴政策、月度申报及冲正；完成客户和上游月度对账、后台分权和首页配置。

每步记录已实现、已通过测试、未验证与不支持的场景；三数据库验证、真实登录端到端流程及支付测试商户验收是独立证据，不由文档标签代替。

### 本轮实现边界

- 新增 `service/subsidy_quote.go` 的纯报价计算：版本化政策快照、企业/月/币种校验、已用与预占共同占用上限、折扣叠加模式、整数金额及时区边界。该函数不读写数据库，不进行资格审批或政府到账确认，也不直接修改客户余额。
- 尚未接入客户支付、订单及账单流程。将来接入必须在同一事务中锁定企业月度预算、保存唯一消费标识与报价快照；单独调用计算函数不能保证并发月度上限，也不能用作生产补贴已完成的证据。
- 本轮验证：Go 1.26.10 执行 `go test ./service -count=1` 通过；新增七组补贴测试覆盖预算作用域、折扣互斥、已用与预占额度、自然月及政策起止边界、最大整数金额、分位舍入、连续报价触顶和非法输入。未进行补贴支付端到端或并发账本验收。

## 1. 项目定位

Quinta AI Gateway 的长期定位是面向企业和平台运营方的 AI 商业化基础设施，逐步从统一网关演进为 MaaS 平台、Agent Marketplace 和 Enterprise AI Operating System。

长期目标：

- AI Gateway：统一接入 OpenAI、Claude、Gemini、Azure、Bedrock 等多类模型和 Provider，提供认证、限流、转发、日志和治理能力。
- MaaS Platform：提供订阅、额度、计量、账单、支付、卡券、发票、收益分成和财务运营能力，支持模型即服务商业化。
- Agent Marketplace：在模型网关和商业闭环之上，支持 Agent 上架、购买、分发、计费和运营。
- Enterprise AI Operating System：面向企业客户提供组织、权限、知识库、审计、分析、成本治理和内部 AI 服务运营能力。

当前 11.2 阶段的核心判断：项目已经具备 Alpha 商业化闭环，下一阶段重点不应继续堆叠模块，而应提升生产支付、结算、审计、国际化和产品体验成熟度。

阶段定义：

- Foundation：核心模型和主流程已建立，可支撑后续迭代，但仍缺生产级集成或完整运营能力。

- Beta Ready：具备更完整的生产集成、审计、国际化、异常处理和运营工具。
- Production Ready：具备生产 SLA、风控、对账、审计、监控、数据导出和长期维护能力。

## 4. Alpha 阻塞项

### Critical

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| 验收测试或前端构建失败 | 直接影响 Alpha 发布 | 每次发布前必须通过后端测试、前端 typecheck 和 build |
| 核心财务页面缺失 en / zh 翻译 key | 面向中英文 Alpha 用户时会影响基本可用性 | Alpha 发布前至少补齐 Billing、Voucher、Invoice、Finance、Subscription 的 en / zh 文案 |
| 菜单权限、页面权限、API 权限不一致 | 可能导致越权访问或误展示 | 发布前执行一次 RBAC 回归测试 |

### Warning

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| Payment Gateway 仍为 Foundation | 不支持生产微信/支付宝自动支付 | Alpha 使用 Mock 和人工银行转账；Beta 做生产支付集成 |
| Invoice Workflow 仅支持人工登记 | 不支持真实数电票、税控或第三方开票 | Beta 或后续独立做 Invoice Provider Integration |
| Dashboard、Finance、Statistics 信息架构仍需收口 | 管理员可能不易区分不同统计入口 | Alpha 可用，Beta 前统一信息架构 |
| 商业页面 UI 组件重复 | 维护成本和体验一致性不足 | Beta 前建设 Commercial UI Kit |
| 多语言包未完全补齐 | 非中英文市场体验不足 | Beta 前补齐全语言 |

## 8. 建议下一阶段开发顺序

范围：

- 支付异常处理。

- 支付安全审计。

- 建立缺失 key 检查。
- 清理硬编码文案。
- 统一商业术语表。

### 12.5 Invoice Provider Integration

目标：在人工开票工作流稳定后，独立建设真实开票 Provider 集成。

范围：

- 数电票、税控或第三方服务商接入预留。
- Provider 抽象。
- 外部回调。
- 失败重试。
- 文件回写。

注意：Invoice Provider Integration 必须独立迭代，不应混入当前 Invoice Workflow Foundation。

### 13.0 Agent Marketplace Foundation

目标：开始从 MaaS Platform 迈向 Agent Marketplace。

范围：

- Agent 商品模型。
- Agent 上架和审核。
- Agent 购买或订阅。
- Agent 使用计费。
- Agent 收益分成。

## 结论

Quinta AI Gateway 当前已经具备 Alpha 商业化闭环，可以进入受控 Alpha 发布准备阶段。下一阶段应优先提升生产支付、审计、结算、UI 一致性和完整国际化，而不是继续新增分散业务模块。
